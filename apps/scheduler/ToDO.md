**Design fix (caught while implementing, not in the original spec text):** the original Architecture.md had `sched daemon --once` route through the same catch-up-gated "startup" logic as the long-running daemon. That's a real bug — since `--once` is documented (API.md, this file's M5) as a system-cron replacement invoked repeatedly, routing it through the catch-up gate meant a task with the *default* `catchup: false` would **never fire** under that usage pattern (the gate would perpetually skip-and-advance its stale slot before ordinary tick logic got a chance). Fixed by splitting `startup()` into `recover_crashed_runs()` (crash recovery only, used by both) and `startup_catchup()` (catch-up gate, used **only** by the long-running `run_forever()`); `run_once()` now does crash-recovery + one unconditional tick. Architecture.md §4 updated to explain this distinction — read it before touching `daemon.py`.

**Verified live** (not just pytest): ran `sched daemon` against a task scheduled ~2 minutes out — fired at T+1.85s past its slot (`tick_seconds=5`), `trigger=schedule`, `status=success` (spec A2). Separately simulated a crashed mid-run (`status='running'` row + stale `running_pid`) and confirmed `sched daemon --once` recovers it to `status='error'`, `error='daemon terminated during run'`, and clears `running_pid`, without touching any task file (spec A3).

**A significant finding from the full end-to-end run, not a code bug:** running the real `github-trending` task against `llama3.2:latest` (the only tool-calling-capable model available in this sandbox), the executor correctly called `web_search`/`fetch_page`, correctly got back "unavailable" error strings (no internet here), and then **the model hallucinated plausible-looking project names and GitHub URLs anyway** instead of following the system prompt's explicit "do not invent facts" / "note the failure and continue with what you have" instructions. I traced the full message flow to confirm: the tool contract, error propagation, and prompt are all working exactly as designed — the gap is the 3B model's instruction-following reliability under tool failure, a widely-known limitation of small models generally, not something specific to this codebase. Deliberately did **not** patch `EXECUTOR_SYSTEM` in Agents.md over this — Agents.md's prompts are meant to be used verbatim, and there's no strong evidence a wording tweak would reliably fix small-model confabulation (vs. it being closer to a capability floor). **Practical implication for anyone deploying this for real:** the default `qwen3:8b` (Agents.md's model table) or another larger tool-calling model is materially more trustworthy for "don't invent facts" behavior than a 3B model — treat any report from a small local model as needing a skim for plausibility, especially early on, and consider this when picking `ollama.model` in `config.yaml`.
