# Phase 0 test plans

Phase 0 answers the questions the spec can't settle on paper. Each spike has a question, the decision it feeds, a method, and **pass/fail numbers set in advance**, so results can't be argued into whatever we hoped.

Spike code is throwaway and lives in `spikes/` (not `internal/`). Results go in `docs/spikes/S<n>-results.md` using the template at the end, and any decision they change goes into SPEC/ADRs in the same commit.

<a id="assisted-labelling"></a>
### Assisted labelling protocol
Measured on `router-200` (2026-10-15): a second blind pass by the same model that wrote the draft matched it on **200 of 200** task types and yes/no fields. It found nothing. The human pass agreed on 96% of task types and disagreed on 39 items, 30 of which the AI had marked as sure. So:
1. **Draft (a):** a strong model labels everything and marks the items it's unsure about (`make_decisions.py`).
2. **Independent pass (b):** a human (`review.py`). With no human available, use a model from a **different family** than the drafter, and never one of the models under test. Report results as provisional until a human has audited at least a random 20 items.
3. **Settle disagreements:** a human sees both answers side by side with the definitions (`adjudicate.py`) and picks one or edits. Definitional rules are applied automatically (web = yes ⇒ tools = yes).
4. **Gold label** = the settled label; else a and b where they agree; items still in dispute are left out of scoring.

Don't count "the AI agrees with itself" as a second labeller, and don't skip human review of items the AI was sure about. Most real disagreements were there.

## S1. Tool calling on small models
**Question:** For models under 7B, is grammar-constrained tool calling more reliable than native tool calling?
**Feeds:** default `tool_strategy` per size class ([MODEL_ADAPTERS.md](MODEL_ADAPTERS.md#tool-calling-strategies)).
**Method:** run `tools-50` × {native, constrained, prompted} × {`llama3.2:3b`, `gemma3:4b`, `qwen3:4b`, `qwen3:8b`} on M1, 3 seeds each, temperature 0.2.
**Metrics:** valid-call rate, right tool, right args, task success (end state matches), false-call rate on the 10 no-tool tasks, median latency.

| Result | Decision |
|---|---|
| Constrained ≥ native + 10 pts task success for < 7B | Keep plan: constrained default for < 7B |
| Within ±10 pts | Native default (simpler, faster); constrained as fallback after a malformed call |
| Native ≥ constrained + 10 pts | Native everywhere; constrained only for models without tool support |
| Any strategy has false-call rate > 10% | Add a "tool needed?" decision before tool selection |

Also: constrained latency overhead must be ≤ 15%, or note the cost. **Time box:** 3 days.

## S2. Proxy compatibility and overhead
**Question:** Does a Go proxy on one port (`/v1/*` + `/api/*`) work with real chat apps, and what does it cost?
**Feeds:** FR-I2/I3, NFR-3, ADR-0002.
**Method:** minimal proxy with one server-side tool (`get_time`). Clients: Open WebUI (OpenAI connection **and** Ollama connection), plus one more chat app you use. 100 scripted chats per client: streaming, model list, stop/cancel mid-stream, thinking output, long answer (> 4k tokens). Overhead measured against a mock backend that streams fixed tokens, so model speed doesn't hide it.

| Pass if |
|---|
| 0 protocol errors in 100 runs per client and connection type |
| Added latency p50 < 20 ms, p99 < 60 ms; time-to-first-token unchanged ± 10 ms |
| Cancel in the client stops generation in Ollama within 1 s |
| Server-side tool use is invisible to the client except as optional progress/thinking text |

**Fail →** document which client/feature breaks; decide whether `/api/*` needs a separate port after all. **Time box:** 3 days.

**Result:** [S2-results.md](spikes/S2-results.md). Passed: no separate port needed, overhead +0.1 to +0.6 ms, cancel reaches Ollama in 0.2 s. Found: the root probe, digest length, `/api/generate`, thinking field names, Open WebUI's background requests and ~11k tokens of client tools per request ([PROXY.md](PROXY.md)).

## S3. JEV decision models on 16 GB
**Question:** Are `tev1`/`tev1:0.8b` fast and accurate enough to be the resident router/judge next to an 8B chat model? What does `noul` mean?
**Feeds:** FR-B6, router tier 3, default decision model per RAM tier, [ORCHESTRATOR.md](ORCHESTRATOR.md#memory-budget).
**Method (M1):**
1. `noul-40` on `tev1` → distribution of `noul` for yes vs. no items.
2. `router-200` on `tev1`, `tev1:0.8b`, `nimble` (if it fits) and **emulated** decisions on `qwen3:4b` and `qwen3:8b`. Measure accuracy (task_type), MAE (difficulty), F1 (needs_*), calibration (ECE), latency p50/p95.
3. Repeat 2 with `qwen3:8b` loaded and generating at the same time (realistic contention).
4. Record memory from `/api/ps` and macOS memory pressure.

| Result | Decision |
|---|---|
| `noul` mean ≥ 0.9 on yes items and ≤ 0.1 on no items | Confirm "noul = P(yes)" in docs |
| `tev1` task_type accuracy ≥ 85% and p50 ≤ 150 ms under contention | `tev1` = default decision model on 16 GB |
| `tev1` < 85% but `nimble` ≥ 85% and fits | `nimble` on ≥ 24 GB only; 16 GB uses `tev1` with lower confidence cut-off and kNN first |
| Emulated `qwen3:4b` within 5 pts of `tev1` | Decision model becomes optional, recommended only for speed |
| Memory pressure goes red with `tev1` + `qwen3:8b` | Default to `tev1:0.8b` on 16 GB |

**Time box:** 3 days (after `router-200` exists).

**Result:** [S3-results.md](spikes/S3-results.md). `tev1` failed the latency and memory rules on 16 GB. Decided: `tev1:0.8b` asking only `task_type` on 16 GB, `tev1` above, a prompt-cache ceiling, and a ≤ 300 ms / ≤ 600 ms latency budget ([ADR-0006](adr/0006-decision-model-on-16gb.md)).

## S4. Memory slots and swap cost
**Question:** Do the slot estimates hold, and how expensive are swaps?
**Feeds:** `memory_budget_gb`, `min_swap_gain`, `hold_seconds`, Ollama settings `doctor` recommends.
**Method (M1, then W1):**
- Load times for `qwen3:8b`, `qwen2.5-coder:7b`, `qwen2.5vl:7b`, `qwen3:4b`: cold (after reboot) and warm (recently unloaded), 5 runs each.
- Memory with KV cache f16 vs. `q8_0` (flash attention on) at 8k and 16k context; quality check by re-running the S1 subset with `q8_0`.
- Confirm whether changing `num_ctx` triggers a reload.
- **Prompt-cache growth** (found in [S3](spikes/S3-results.md#memory)): Ollama-reported size and free memory over 200 varied requests for each model, MLX and GGUF builds, with the default cache budget and with a cap (if the Ollama version supports one). Latency of a fresh request at each point.
- Resident + each primary: does it stay under budget without memory pressure or swap to disk?
- W1: a model that doesn't fit in VRAM: tokens/s vs. fully in VRAM.

| Pass if |
|---|
| Resident + any one 7–8B primary at 8k fits the budget with no memory-pressure warning, **after** 200 varied requests (prompt caches full) |
| Warm swap ≤ 4 s on M1 (otherwise raise `min_swap_gain` and `hold_seconds`) |
| `q8_0` KV costs ≤ 2 pts task success on the S1 subset (otherwise don't recommend it) |

**Time box:** 2 days.

**Result:** [S4-results.md](spikes/S4-results.md). Memory pass failed on 16 GB for 8B and vision models (budget 10.5 → 8 GB, default primary a 4B), swaps take 4–7 s for 7–8B models (`min_swap_gain` 0.15, `hold_seconds` 120), `num_ctx` changes reload, GGUF models don't grow, `q8_0` KV not recommended by default ([ADR-0007](adr/0007-16gb-memory-budget-and-model-defaults.md)). Not run: cold-from-reboot loads and W1.

## S5. Hermes Agent teardown
**Question:** Where exactly must noskill beat Hermes to be worth building standalone (ADR-0003)?
**Method:** install Hermes on M1, W1 and L1 following its docs, with Ollama `qwen3:8b`. Record install time and steps, failures, idle memory, cold start, and success on 10 `tools-50` tasks (real tools where it has them). Trigger its skill creation once and keep the skill it writes. Check whether Windows works natively or needs WSL.
**Output:** a "beat this" table: each row is one of our goals (G1–G8) with Hermes's measured number and noskill's target. Plus a list of learning ideas to copy. **Time box:** 2 days.

**Result:** [S5-results.md](spikes/S5-results.md), macOS only. Hermes needs 64k context and sends 11–13k tokens before the first word, starts in 1.6 s, keeps 134 MB resident, and got 8 of 10 real tasks right with a 4B model; its learning has no verification. ADR-0003 stands. Not run: W1/L1.

## S6. qBittorrent Web API and series matching
**Question:** Does everything anime-tracker needs work on your qBittorrent version, and can decisions match RSS items reliably?
**Feeds:** [anime-tracker](../skills/anime-tracker/SKILL.md) implementation spec.
**Method:**
1. On your qBittorrent version (and the latest 5.x in a VM): `app/webapiVersion`, `rss/items`, `rss/setRule` with a `noskill: test` rule, `rss/matchingArticles`, `rss/removeRule`, `torrents/info?filter=completed&category=…`, torrent state after a share limit is reached, `setLocation`, `renameFile`, `torrents/delete` with `deleteFiles=false`. Localhost auth bypass on and off.
2. "Run external program on torrent finished" with `noskill hook qbittorrent-finished "%I"` on M1, W1, L1.
3. `rss-100`: `decide("same_series")` with `tev1` vs. a regex built from AniList aliases.
4. Resolution: share of series in your feeds that have 480p releases; a rule whose `mustContain` requires `480p|848x480|854x480|640x480` matches only those; `torrents/add` for a 720p fallback episode, then adding that episode to `previouslyMatchedEpisodes` stops the rule grabbing the same episode's 480p release later.
5. Filing loop on a real external drive (exFAT, mounted as `/Volumes/RED` or the Windows/Linux equivalent): 5 finished torrents in `~/Downloads` → copy to `<folder>/<Title>/…part` → hash check → rename → `torrents/delete deleteFiles=false` → OS trash, one at a time. Unplug the drive mid-copy once; remount it at a different path once.

| Pass if |
|---|
| Every endpoint above works, or has a documented substitute for your version |
| The 480p rule and fallback never download the same episode twice |
| Filing loop: every file ends up renamed in the folder with a matching hash, every original is in the OS trash (recoverable), and nothing is trashed when the copy failed |
| `same_series` precision ≥ 0.98 at recall ≥ 0.90 (false matches waste downloads, so precision matters more) |
| Decisions + regex together beat regex alone on precision |

**Time box:** 2 days.

## S7. Daemon, scheduler and notifications on each OS
**Question:** Can the daemon install without admin rights, survive reboot and sleep, and send notifications with **Approve/Skip** buttons on all three OSes?
**Feeds:** FR-J2/J3, FR-A6 (whether notification actions are in v0.1), [PLATFORMS.md](PLATFORMS.md).
**Method:** skeleton daemon + a job every 5 minutes. Install via launchd (M1), Task Scheduler (W1), systemd `--user` (L1). Reboot, sleep 30 min, wake, log out/in; check missed-run policy. Notifications with two action buttons from an unpackaged binary. macOS may need a small helper `.app` bundle for `UNUserNotificationCenter`, and Windows toasts need an AppUserModelID registered via a Start-menu shortcut.

| Pass if |
|---|
| Install/uninstall without admin on all three |
| Job fires within 60 s of schedule after wake; missed-run policy correct |
| Action buttons work on at least macOS and Windows. If not, v0.1 approvals use CLI + plain notifications, and buttons move to the tray (v0.2) |

**Result:** [S7-results.md](spikes/S7-results.md), **macOS only, partly run.** Install/uninstall as a launchd user agent passes with no admin (0.1 s / 0.03 s, nothing left behind but Trash items); on-schedule drift 0.84 s (own wall-clock scheduler) and 5.3 s (launchd calendar). Notification shown (user-reported) but no Approve/Skip click in the log. Not run: sleep/wake and missed runs, reboot/log out. Found: the helper `.app` is mandatory and must be registered with LaunchServices, or the permission request fails silently; the permission prompt is a banner that fades in seconds and an ignored request counts as a denial. Not run: Windows, Linux.

**Time box:** 3 days.

## S9. Sandbox feasibility
**Question:** Can every cell of the [per-OS sandbox table](SECURITY.md#per-os-sandbox) be built **without admin rights**, does it stop the attacks in the security test suite, and what does it cost per call?
**Feeds:** FR-S4, NFR-7, the `[sandbox] mode` default, whether Windows domain filtering stays advisory in v1.
**Method:** one attack script (uv-managed Python) plus a small Go launcher per mechanism. The script tries to read `~/.ssh/id_ed25519`, write outside `work/`, open a raw socket, connect to a non-allowlisted domain **while ignoring proxy variables**, fork 1000 processes, and allocate 4 GB. It also does legitimate work: a 20-line CSV transform and an HTTPS GET to an allowlisted domain through the egress proxy.
1. **macOS (M1):** `sandbox-exec` with a generated SBPL profile (deny by default; `work/` read-write; uv cache and system libraries read-only; network only to the proxy's localhost port). Check that uv's Python and Node start under it.
2. **Linux (L1, plus an Ubuntu 22.04 VM on kernel 5.15, plus inside a Docker container):** detect the Landlock ABI version; file rules on all; TCP connect rules where the kernel is ≥ 6.7; bubblewrap with `--unshare-net` and the proxy reached through a bind-mounted Unix socket; cgroup limits via `systemd-run --user --scope`.
3. **Windows (W1):** launch from Go into an AppContainer (`CreateAppContainerProfile` + `PROC_THREAD_ATTRIBUTE_SECURITY_CAPABILITIES`) inside a Job object; grant the AppContainer SID access to `work/` and the runtime folder only. Answer: does uv's Python run there, and can an AppContainer reach the localhost egress proxy without the admin-only loopback exemption (alternatives: a named-pipe forwarder, or a Windows Filtering Platform rule)?
4. **Egress proxy:** CONNECT allowlist tested with Python `requests` and `httpx`, `curl`, `uv pip install`, and Node's built-in `fetch` (which ignores proxy variables by default). Clients that bypass the proxy must be stopped by the OS layer, not trusted to comply.
5. **Cost:** extra start-up time per sandboxed call, and copy-in time for 100 MB of inputs.

| Pass if |
|---|
| All attacks blocked on macOS and Linux (kernel ≥ 5.13 or bubblewrap present), with no admin/root |
| Windows: file isolation works without admin; network on/off works; the domain-filtering question has a clear answer |
| Legitimate work succeeds under every mechanism (Python and Node) |
| Sandbox start-up overhead ≤ 150 ms p50 per call; copy-in of 100 MB ≤ 1 s on SSD |
| A script that ignores proxy variables still can't reach a non-allowlisted domain (macOS; Linux ≥ 6.7 or bubblewrap) |

**Result:** [S9-results.md](spikes/S9-results.md), **macOS only**. All 24 attacks blocked with no admin rights. Python (stdlib, requests, httpx, uv install) and Node work through the proxy. Overhead +41–45 ms, copy-in of 100 MB 13–92 ms. Found: macOS refuses memory rlimits (a watchdog is needed), a script allowed to fork can leave a confined detached process, and the proxy must refuse names that resolve to local addresses ([ADR-0008](adr/0008-macos-script-sandbox.md)). Not run: Linux, Windows.

**Fail →** macOS: if `sandbox-exec` is unusable, learned code runs as WASM only and other scripts need approval per run. Linux: require bubblewrap on kernels without Landlock. Windows: if Python won't start in an AppContainer, ship the runtime in a noskill-owned folder with the right ACLs; if domain filtering can't be enforced, scripts with `network` need approval per run. **Time box:** 2 days.
